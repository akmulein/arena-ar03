# AR-03: единственный запуск пилота

Архитектура зафиксирована: доверенные train/public/private оценщики работают на хосте; Codex, оркестратор и исследователи — в существующем изолированном researcher; кандидатский код — только в штатном CPU DockerRunner. Новых сервисов, брокеров и образов нет. В пилоте включён только train: прежние фиксированные 20 IDs и общий лимит 4 кандидата. Public/private не активируются.

Команды выполняются из корня AR-3. Для стандартного расположения задайте `export AR03_RESOURCES="$(pwd)-operator"`; для другого расположения укажите свой внешний каталог. Подготовка с нуля и экспорт для сдачи описаны в [документации кейса](../README.md).

Единственная команда запуска подготовленного пилота (выполняет владелец, когда разрешает эволюцию):

```sh
.venv/bin/python -B cases/ar-03/deploy/operatorctl.py run --root "$AR03_RESOURCES/runs/pilot-01" --source-ref 'Ручной запуск пилота владельцем проекта'
```

Команда поднимает существующие компоненты, снимает прежнее разрешение, проверяет фактическую изоляцию и запрашивает у доверенного API разрешение, привязанное к текущим Container/Image ID, конфигурации и операторским процессам. При любом отказе Codex не запускается. Отдельные arm/research и standalone train закрыты. Простой authorized.json не даёт права на оценивание. Перезапуск контейнеров или изменение условий аннулирует доказательство и разрешение; их нельзя восстановить простым возвратом старых файлов. Локальные неизменяемые IDs образов берутся из операторского images.json после bootstrap; для существующей установки сохраняется deploy/images.json. Команда run ничего не собирает.

В идентификацию входят State.StartedAt контейнеров и время запуска операторских процессов. После изменения доверенного кода или конфигурации старые процессы требуют services-down и start с тем же --root; повторная verify без перезапуска запрещена. Затем используется штатная команда run. Runner-assets допускает только прежние восемь файлов моделей; посторонние файлы блокируют запуск.

При каждом запросе нового оценивания, перед каждой страницей и перед передачей предсказания метрике проверяется тот же профиль. Фоновый контроль отзывает разрешение при нарушении; уже работающие runner-контейнеры только этой кампании останавливаются. Если Docker недоступен, новые страницы и передача ответа метрике блокируются. Researcher не получает реализации метрики, операторских ключей, public/private или закрытых артефактов. Журнал и открытый train доступны ему только для чтения. Проверки запускаются доверенной стороной; Python-проба внутри researcher использует -I и не импортирует код из изменяемого workspace.

Codex запускается только внутри проверенного researcher с `--dangerously-bypass-approvals-and-sandbox`: вложенный bwrap не может создать namespace при действующих ограничениях Docker. Это снимает внутренние подтверждения Codex; внешние mounts, UID, capabilities, seccomp, сеть и fail-closed сохраняются. На хосте этот флаг не используется, дополнительные привилегии контейнеру не выдаются. Он применяется после проверки разрешения операторским API; кандидаты по-прежнему исполняются исключительно в отдельном штатном CPU DockerRunner.

Для исследовательского Python используется /opt/arena/.venv/bin/python; NumPy 2.3.5 хранится в существующем томе /codex/research-packages и подключается через PYTHONPATH только при запуске Codex. Недостающий закреплённый wheel получает оператор на хосте; установка внутри researcher выполняется с --no-index, без расширения сетевой политики и изменения образа. При занятом единственном слоте клиент evaluate ждёт Retry-After и повторяет техническую отправку; сервер сохраняет исходный measurement ID. RETRYABLE означает неподтверждённую отправку, а не новую версию или нулевой score. Завершённые результаты повторно не вычисляются.

Операторская команда reference измеряет неизменённый ways/baseline отдельно от журнала предложений, используя ту же штатную фабрику train-оценивания, CPU DockerRunner, frozen metric, вход и общий слот. Она требует действительный fail-closed допуск и явный --source-ref, не запускает оркестратор и не выдаёт разрешение на эволюцию. Повторный вызов возвращает существующий checkpoint по идентичности baseline и train-набора. Агрегированный референс сохраняется в baseline-reference.json у оператора и в campaigns/pilot-01; сырой результат и визуализации остаются в private/state/baseline-reference и private/visualizations/train/baseline-reference. При штатном продолжении разрешённый JSON передаётся researcher без операторских данных.

Проверка изменённой конфигурации без эволюции:

```sh
.venv/bin/python -B cases/ar-03/deploy/operatorctl.py verify --root "$AR03_RESOURCES/runs/pilot-01"
```

Авторизация Codex выполняется в том же контейнере после успешной verify; OAuth-том сохраняется. Если вход уже выполнен, повторять его не нужно:

```sh
.venv/bin/python -B cases/ar-03/deploy/operatorctl.py login --root "$AR03_RESOURCES/runs/pilot-01"
```

Для временной остановки завершите CLI сочетанием Ctrl+C в терминале запуска: команда снимает разрешение в finally. Принятые расчёты завершаются только при сохранении безопасных условий. Возобновление — та же команда run, без очистки журнала или сброса лимита. Окончательная остановка закрывает журнал и не предназначена для возобновления:

```sh
.venv/bin/python -B cases/ar-03/deploy/operatorctl.py stop --root "$AR03_RESOURCES/runs/pilot-01" --source-ref 'Окончательная остановка владельцем проекта'
```

Прогресс и операторские визуализации:

```sh
.venv/bin/python -B cases/ar-03/deploy/operatorctl.py progress --root "$AR03_RESOURCES/runs/pilot-01"
open "$AR03_RESOURCES/runs/pilot-01/private/visualizations/train"
```

Актуальное доказательство безопасности и результаты отрицательных проверок находятся в $AR03_RESOURCES/runs/pilot-01/private/security/. Закрытые артефакты остаются в private/visualizations, первичные результаты — в private/state, графики TEDS и родословная — в progress. Public AUC в train-only пилоте отсутствует. Основная кампания требует отдельного согласования лимита, K и N и автоматически не запускается. README и ядро Arena не менялись.
