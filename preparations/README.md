# Каталог переиспользуемых результатов подготовки

Перед подготовкой нового материала прочитай этот README и доступный реестр кампании: `<campaign_dir>/preparations/README.md`. Если подготовка не нужна, каталог не используется. Реестр помогает найти и явно выбрать уже опубликованный результат: индекс, признаки, разобранный документ, скомпилированную программу или другой разрешённый материал. Он не заменяет [публикации и доверенные квитанции build](../common/runner-contract.md) и не запускает подготовку автоматически.

При подготовке кампании создай рабочий README по таблице ниже либо запиши, что каталог не используется. Все worktree читают один абсолютный путь к этому реестру. Для разрешённого переиспользования между кампаниями добавь ссылку на доступный прежний реестр и его публикации; не копируй закрытые данные или операторские журналы. В Git допустимы только открытые описания и ссылки без секретов. Сами материалы и квитанции остаются в настроенных хранилищах.

## Реестр

Одна строка описывает одну публикацию либо одну ещё не завершённую попытку подготовки. Записи добавляются по фактическим квитанциям и проверкам; отсутствие результата не заполняется вымышленной публикацией. Ошибочную попытку сохраняют, исправленную версию связывают с ней новой строкой. При совместной работе назначь одного редактора таблицы, а остальные участники передают ему ссылки на свои результаты.

| ID, кейс и назначение | Формат и версия структуры | Исходные материалы и условия использования | Снимок кода подготовки и параметры | Публикация и квитанция | Зависимости и затраты | Статус build | Проверка чтения решателем | Использование, замеры и findings | Ошибки и ограничения |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

В рабочем README заполняй поля так:

- **ID, кейс и назначение:** короткое устойчивое имя записи, кейс и задача материала. ID записи не является новым номером решения: кандидат сохраняет номер регистрации в журнале.
- **Формат и версия структуры:** тип файлов, схема и её версия, необходимые зависимости читателя.
- **Исходные материалы и условия использования:** ссылки на разрешённые входы и зафиксированные условия; ответы, эталоны и состояние public/private-примеров в каталог не входят.
- **Снимок кода подготовки и параметры:** зарегистрированный кандидат, путь к неизменяемому снимку, команда или программа подготовки и фактические параметры.
- **Публикация и квитанция:** выданный сервисом `output_digest`, путь `/assets/derived/<output_digest>` и ссылка на квитанцию. До успешной публикации идентификатор и путь явно пусты; ссылка на квитанцию сохраняется и для `RUNNING`, и для `FAILED`.
- **Зависимости и затраты:** ссылки на исходные квитанции, их `dependency_receipts`, собственные и суммарные токены и время, признаки полноты измерения. Неизвестные затраты помечаются неизвестными. Реестр не создаёт второй счётчик поверх квитанций.
- **Статус build:** фактический `RUNNING`, `FINISHED` или `FAILED` из квитанции, время проверки статуса и ссылка на неё.
- **Проверка чтения решателем:** точный снимок читателя, проверенный путь и формат, команда и сохранённый результат. Успешный build сам по себе не доказывает совместимость с читателем.
- **Использование, замеры и findings:** ID кандидатов, использовавших материал, ссылки на разрешённые измерения и выводы. Score принадлежит связке «решатель + материал»; самостоятельного «лучшего score» материала здесь нет.
- **Ошибки и ограничения:** фактическая ошибка и ссылка на свидетельство, несовместимые читатели, непроверенные свойства и следующий шаг. Не заменяй установленную ошибку предположением об инфраструктуре.

## Явный выбор результата

1. Сравни назначение, формат, разрешённые исходники и условия доступных публикаций с гипотезой. Укажи, меняется ли представление данных, способ чтения прежнего представления или только другая часть решателя.
2. Для выбранного харнеса оператор должен включить `supports_asset_selection` и подключить общее хранилище публикаций с прежним журналом квитанций. Для результатов измеряемой подготовки также нужен `supports_build`. Выбирай только реально опубликованный совместимый результат.
3. Укажи выданный идентификатор в `solution.json`, в отсортированном списке `parameters.asset_digests`. Зарегистрируй новый снимок до его build или замера. Если выбирается результат измеряемой подготовки, в кандидате должен быть собственный `build.py`; он может использовать выбранный материал, не пересоздавая его. Выполни штатный `evaluator.build submit` для зарегистрированного кандидата по [инструкции развёртывания](../deploy/README.md#необязательный-train-сервис-и-подготовка-материалов).
4. Build получает каталог вывода в поле `build_dir`, а не `output_dir`. Он записывает только свой результат; публикацию выполняет доверенный сервис после успеха. При решении примера выбранная зависимость читается в `/assets/derived/<output_digest>`, собственный результат build — в `/assets/prepared`. Каталог `/output` существует только во время build.
5. Проверь настоящую цепочку `build → публикация → чтение конкретным решателем` на разрешённом небольшом входе. Для кандидата это зарегистрированная проверка с сохранённым результатом; при подготовке инфраструктуры используй отдельный синтетический пример. Сохрани квитанцию, статус и доступную диагностику сбоя. До этой проверки не объявляй материал пригодным только по наличию файлов.
6. Добавь ссылки на новую квитанцию, проверку чтения и кандидата в реестр. Доверенный учёт включает собственную подготовку и уникальные транзитивные зависимости один раз в каждой оценке кандидата. Переиспользование сохраняет происхождение и затраты, не превращая материал в бесплатный импорт.

Каталог не угадывает тождество двух сборок по похожему коду и не пересобирает их автоматически. Повторное использование начинается с явного выбора уже опубликованного результата.
